# simai-env v1.13.0

Release date: 2026-09-22

## Summary

A security and operations release produced by a production-readiness audit.

- **Site isolation.** Every new site runs PHP-FPM, cron and queue workers as
  its own Unix user; project roots are `0750`. Owners (`owner create`) group
  several sites under one account with SSH deploy access, like users in
  hosting panels. `site isolate` moves existing sites, with rollback.
- **Three root escalation paths closed**: runtime observer storage under
  `/home/simai`, symlinked `.env` files, and `/home` owned by the site user.
  `access remove` can no longer delete a live site through a bind mount.
- **Data backups**: `backup data` (database + files, retention, checksums,
  optional `age` encryption and rsync-over-SSH off-site copy),
  `data-verify --restore-test`, `data-schedule`, `data-restore`.
- **Bitrix `short_open_tag`** is no longer lost after `site php-ini-set` or
  `site fix`; Bitrix CLI gets it from a managed `conf.d` file.
- **nginx**: hidden files and dumps denied at any depth, no PHP in WordPress
  uploads, Bitrix service directories denied, and the catch-all now also
  rejects unknown hosts on port 443.
- **Supply chain**: NodeSource via a fingerprint-pinned keyring (no
  `curl | bash`), Node 22 default, installer/updater download the exact
  resolved commit.
- **`self migrate`** runs after every `self update` and brings existing hosts
  in line (catch-all, `/home` owner, logrotate, observer storage, Bitrix pools
  and cron).

Full list: `CHANGELOG.md`.

## Update

```bash
sudo /root/simai-env/simai-admin.sh self update
```

`self update` runs `self migrate` automatically. Then, per site, after a
`backup data`:

```bash
sudo /root/simai-env/simai-admin.sh site isolate --domain <domain>                  # plan
sudo /root/simai-env/simai-admin.sh site isolate --domain <domain> --confirm yes    # own user
sudo /root/simai-env/simai-admin.sh site isolate --domain <domain> --owner <name> --confirm yes
```

Deploy scripts that wrote into sites as `simai` must run as the site's owner
(see `docs/commands/owner.md`).

Behaviour changes to note:

- HTTPS requests for a hostname without its own certificate are now rejected
  instead of being answered by the first TLS site.
- `site db-rotate` is blocked for Bitrix and WordPress (it cannot update
  their PHP config files).
- `site add` refuses project paths outside `WWW_ROOT`, `/var/www` and `/srv`
  unless `SIMAI_ALLOW_EXTERNAL_SITE_PATH=1`.
- `SIMAI_SITE_ISOLATION=no` keeps the shared-user mode for new sites.

## Verification

- repository CI (Bash syntax, ShellCheck, smoke, correction regressions with
  new security contracts, registry dispatch harness) on Ubuntu 22.04 and 24.04;
- end-to-end tests in systemd containers with nginx, PHP-FPM, MySQL, cron and
  sshd on 22.04 and 24.04: isolation, owners, SFTP ACLs, Laravel queue,
  Bitrix `short_open_tag`, backups with restore, host migrations;
- `testing/run-regression.sh full` (55 steps, including the new `features`
  mode) on the regression host;
- rollout on a host with seven Bitrix/Laravel sites: all sites answered
  identically before and after isolation.

## Known limitations

- `SIMAI_STRICT_HANDLERS=1` (errexit inside command handlers) is still
  opt-in: 5 of 14 read-only commands stop early with it enabled.
- Updates still follow the `main` branch; signed release tags are planned.
- No built-in monitoring or alerting.

## Rollback

Before any site is isolated, restore the pre-update archive printed by
`self update` (`/root/simai-backups/simai-env-preupdate-*.tar.gz`) to return
to v1.12.78.

After sites are isolated, do not roll back the code: v1.12.78 regenerates
PHP-FPM pools and cron files for the shared `simai` user, which cannot read
isolated project directories. Fix forward instead, or restore affected sites
from `backup data`.
