# simai-env v1.15.0

Release date: 2026-10-19

## Summary

Every command now runs fail-fast and explains what it will change before it
changes anything.

- **Preview by default.** Commands that change state print a plan and exit 0
  unless `--confirm yes` is given. `--dry-run yes` forces a preview; commands
  with their own dry run (`site remove`, `site db-*`) print their detailed plan.
- **Fail-fast handlers.** Each command runs in a fresh Bash with
  `set -euo pipefail`; a failing step stops the command instead of being
  reported as success. `scripts/ci/errexit_lint.py` keeps the patterns that
  break under this mode out of the code.
- **Locks.** Site operations share a protected lock; host operations exclude
  them. Interactive callers get exit 75 at once; cron and automation wait up to
  `SIMAI_LOCK_WAIT` seconds (default 600).
- **Machine results.** `--output json` returns `simai-command-result/1`
  without secrets. The registry records effects, confirmation, lock and
  verification for every command; `self ai-catalog` publishes the read-only
  AI First 1.0.0 pilot.
- **Bitrix request budget.** nginx, PHP-FPM and PHP use 300 seconds;
  `site config-normalize` repairs existing pools (duplicate keys removed, site
  overrides kept).
- **MySQL exposure.** `db network-plan` shows listeners and connections;
  `db network-localize --ack-no-external yes` binds MySQL and MySQL X to
  127.0.0.1 with a configuration backup, effective-value check and rollback.

## Breaking change: confirm your automation

Before updating, find scripts and cron entries that call `simai-admin.sh`
with a command that changes state and add `--confirm yes`. Without it they
print a plan and change nothing.

Managed jobs are handled for you: `self migrate`, which runs after
`self update`, adds `--confirm yes` to simai-managed scheduler, backup and
observer cron entries after saving the originals in
`/var/backups/simai-system/cron-confirm/`. This also works when the update is
started by a 1.14.x host, whose update handler calls `self migrate` without
`--confirm`.

```bash
grep -R "simai-admin.sh" /etc/cron.d /etc/crontab /var/spool/cron 2>/dev/null
sudo /root/simai-env/simai-admin.sh self commands | less   # "confirmation": "required"
```

## Update

```bash
sudo /root/simai-env/simai-admin.sh self update --confirm yes
```

On 1.14.x hosts `self update` needs no flag (the old handler applies).

## Verification

- CI: Bash syntax, ShellCheck, errexit lint, smoke and correction
  regressions, option validation for all 161 commands, registry dispatch.
- Container end-to-end matrix on Ubuntu 22.04 and 24.04 (`testing/containers`),
  18 cases including `upgrade_e2e`: a 1.14.0 host with managed backup and scheduler cron
  is updated through the old handler path; cron is confirmed and the scheduled
  backup command creates a backup.
- `testing/run-regression.sh full` on the regression host (62 checks): the
  host was updated from 1.14.0 through its old `self update` handler and its
  scheduler cron was confirmed automatically.
- Production-like rollout on the test host (owner-level isolation, six Bitrix
  sites normalized, MySQL restricted to localhost, canary backup/restore and
  code rollback).

## Rollback

Restore the pre-update archive printed by `self update`, then restore the
original cron entries from `/var/backups/simai-system/cron-confirm/`:
1.14.x rejects the unknown `--confirm` option, so confirmed cron lines would
fail after a rollback. Settings changed by `site config-normalize` and
`db network-localize` stay in place; their recovery archives are under
`/var/backups/simai-system/`.
